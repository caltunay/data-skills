# Decisions

## Design decisions

1. Build our own data skills, phased. Flow skills call ours by name. Descriptions avoid clashing with built-ins.
2. One main flow. The plan sets the question type; later steps load its checks. v0 branches: descriptive and experiment.
3. Cycling back adds a dated plan revision entry, no restart.
4. Upstream: inventory both repos and check licenses first. v0 rebuilds only what the flow needs.
5. One path for connected and copy-paste use: `run-or-hand-over` covers queries and files.
6. Productionisation and monitoring: out of scope until v2+.
7. Connectors: rely on each agent's marketplace. No recipes. Hand-over mode covers gaps and admin blocks.
8. One `DATA-MAP.md` with fixed sections, including Conventions. Format version on line 1, with migrations.
9. Every data map entry has a verified date and source. Retro proposes, the user approves. Flag entries older than 90 days or contradicted by data.
10. User files live in `data-work/` in the user's project, committed and shared by the team. Never in the skills repo.
11. One folder per analysis: `analysis.md`, `queries/`, `outputs/`. No raw chat transcripts.
12. Assumptions: a table with alternatives required for high-impact rows.
13. `outputs/` git policy chosen at setup, default excluded. Aggregates by default; ask before saving row-level data.
14. Chat apps are first-class: skills install by upload in claude.ai and ChatGPT. `DATA-MAP.md` lives in the chat app's Project files.
15. Depth (quick, standard, deep) set by `/grill-the-ask`.
16. `shaping-data`: one skill, a tool-agnostic core (analysis table spec) plus one file per tool. All five tools in v0.
17. Style: sqlstyle.guide and PEP 8 by default; team overrides in Conventions; dialect per source in `DATA-MAP.md`.
18. v0 is 15 skills. Router and other off-flow skills in v1.
19. Testing: 3 eval cases per flow skill (2 flawed, 1 clean), run by hand in 4 agents, plus 3 real asks on public data.
20. Names: repo `caltunay/data-skills`; commands `/setup-data-work`, `/grill-the-ask`, `/plan-analysis`, `/run-analysis`, `/review-analysis`, `/retro-analysis`. "datafolx" is reserved for another product.
21. Never call a connector or data tool before the user names the source. Never build options from visible connectors.
22. Never fill in company, product, table or source names the user has not said in this conversation.
23. Setup asks first how to set up the map: connect, describe, paste a schema, or a mix.
24. Every flow step checks for `DATA-MAP.md` and `analysis.md`, says what it found, and offers setup if there is no map. Outside the flow, no map means silence.
25. Chat app is defined by situation (no user project folder), not by file access. Each flow step offers its files as downloads and tells the user to save them to Project files.
26. Standard and deep depth always show the full 7-column assumptions table.
27. `/run-analysis` is goal-driven: it states its goal and keeps going until the success checks pass, stopping only for pastes or answers.
28. Readout: `/run-analysis` drafts `readout.md`; `/review-analysis` checks it word by word and marks it final. One layout, wording adapted to the audience set in grilling.
29. Progress line in `analysis.md` Meta; every new session resumes from it.
30. `question-types` covers all six types: one skill, a selector in `SKILL.md`, one file per type with method cards. Full cards for common methods, short cards plus a specialist-review flag for advanced ones. In v0.1, with method-choice evals.
31. One neutral example domain: an invented online shop and subscription app. A private gitignored `.blocklist` is checked by `scripts/self-check`.
32. `grilling` fires on data asks only. Descriptions are tuned so generic data asks do not trigger ours over built-in data skills.
33. v0.2 is built on its own branch with its own pull request into `spec/v0`. Every new skill is marked experimental until it has passed its evals.
34. `viz` is a model-invoked data skill, not a command: one core file for chart choice and checks, plus one file per tool. Excel, Tableau and Power BI run in hand-over mode.
35. `/storytell` rewrites a final readout for one audience and format. It never raises a claim above the ceiling in `analysis.md`, and every number keeps its uncertainty.
36. `/improve-code` works in a fixed order: intent, correctness, style, performance. Changes are surgical, shown as a diff, and proven equivalent with check queries unless a behaviour change is the point.
37. `/ask-data-skills` only routes. It recommends one command and the next one. It never does the work.
38. `/wayfinder-data` maps big, vague work as decision items and resolves them one at a time with the user. It ends with ready `/grill-the-ask` prompts.
39. `/handoff` writes `handoff.md` so a colleague or a fresh session can resume from the Progress line.
40. Predictive method cards: gradient boosting, classification metrics and calibration are full cards. Feature importance is never causal.
41. Upstream backlog: every item is absorbed, built or dropped with a reason. One new skill, `metric-design`. Dashboards go into `viz`.
42. Plugin manifests ship for Claude Code and Codex. The skills stay plain SKILL.md files, so every other install route still works.
43. Two worked examples with seeded, invented data are the demo. Their queries are really run.
44. CI runs the self-check on every pull request and push. The private blocklist comes from a repository secret. A published release attaches the ZIPs by itself.
45. The eval runner approximates skill loading and grades with a judge model. It does not test triggering. Keys come from the environment only.
46. Contributor docs and templates carry the hard rules, so outside contributions meet them by default.
47. Validation has a data-check floor at every depth, quick included: table audit, one real entity across tables, one day, the daily series, join checks, category totals, assumption checks and the reconcile. Quick gets a compact form, never a skip. The daily series runs before any segment scan on a drop.
48. Ladder rungs 2 to 4 test the data against an independent path (raw rows or a separate query), never the frame the table was built from. The review recomputes the headline numbers by an independent route as a standard step.
49. `run-or-hand-over` asks two separate questions. Can I run things here? Always try first: a code tool or sandbox with attached files counts. Where do files persist? In a chat app, create each file and offer it as a download; print only if that fails. Being in a chat app never means "I can't run code".
50. After the user confirms something, the skill hands back the updated file. It never asks the user to edit a saved file by hand.
51. `question-types/SKILL.md` holds a compact line per method (when to use, checks that must pass, claim allowed), so the method cards work without file access. `/plan-analysis` copies the checks into the success checks at plan time.
52. Every flow step ends with the same go-ahead question at every depth: A) yes, run the next command; B) change something; C) add a check, segment or question.
53. Every question has one real recommended default with a reason. No hedges, and no question without a default, the deadline included.
54. Period comparisons handle seasonality by default (the same weeks last year, or the same weekdays). A plain back-to-back comparison is allowed only with a flag that it ignores seasonality.
55. The assumptions table holds only real assumptions. Claim rules go in a claim ceiling line in Meta. Impact is rated by size on the headline.
56. The reconcile check names the count that must match the trusted number (raw or cleaned) and why. Every spec correction is a dated Plan revisions row. Requester and date in Meta are never blank.
57. The readout has at most 5 key numbers, strict for an exec audience; the rest go to an Appendix. The default readout serves the audience set in grilling. `/storytell` is for other audiences and formats.
58. The readout's Method section claims only what ran. The review shows every changed sentence as a "was" and "now" pair, and every "not supported yet" leadership answer names the cheapest way to answer it.
59. Setup gives no git advice in chat apps. Every join in the data map starts `unverified` until a query checks it. The dialect question offers one real option per engine.
60. Retro puts each entry in the right section: Conventions hold style only, analysis rules go in Rules or Gotchas, and nothing is duplicated. Every reason it gives must be true for this run.
61. `/review-analysis` reviews from the files only, never from chat memory, and always recomputes the 3 to 5 headline numbers by an independent route. A fresh context is recommended at standard and deep depth: a subagent if one is available (optional, never relied on), otherwise a new chat in the same Project.
62. `analysis.md` carries a Review pack appendix with the exact code and data source of each headline number, so a fresh reviewer can see the code in a chat app.
63. Readout visuals follow the `viz` rules: at most 3 charts for exec, a takeaway title, one annotation, image files linked with alt text, and a chart replaces number rows that say the same thing.
64. Readouts use portable markdown: callouts as bold-labelled blockquotes (Answer, Caveat, Ask), at most 3; the status as a bold label (`**Status: DRAFT**`, `**Status: FINAL**`); bold only for one takeaway per section. App-specific exports are v0.4, in `/storytell`.
65. The readout has one source, `readout.md`, and a `.docx` built from the same text with the charts embedded. The review edits the `.md` and rebuilds the `.docx`. With no code tool, the `.md` plus the chart code is the output.
66. `/grill-the-ask` never analyses. With files attached it notes only what they contain (columns, possible duplicates, date range). An early finding anchors the whole analysis.
67. `analysis.md` has a Decisions section: every question and answer, word for word, per round, echoed back exactly before moving on. A paraphrase ("this week" written as "later") is a data error.
68. The setup choice (A, B or map found) is written to Meta and setup is never offered again once it is set. `/retro-analysis` never offers setup: it builds the map itself.
69. The retro map follows the template layout: one entry per source, grain and key facts under Tables, table rows and never loose bullets.
70. `/plan-analysis` writes a hypothesis tree before the method options (standard and deep): support and refute conditions per node, at most 3 levels and about 12 nodes. The user picks the paths. Status per node is kept in `analysis.md` and checked by the review. Quick depth keeps a flat list of up to 3.
71. When an answer conflicts with an earlier one, contradicts the data map, or makes no sense, the skill says so plainly and asks one question at a time until it is clear, then returns to rounds.
72. The data map holds the organisation's goals (mission, north star, targets, horizon). `/grill-the-ask` links the ask to a goal when one exists and records it in Meta.
73. The data map holds Funnels and Key queries (3 to 5). Setup asks for both. Retro proposes additions.
74. The readout skeleton is optional. It uses placeholders only and never an invented number. It exists to test the story against the decision before any work.
75. Skills find `data-work/` in the current folder, then upward. A team map can sit above project maps. The nearest map wins for conflicts and the skill says which one it read. Setup asks how the user organises work.
76. `/wayfinder-data` also handles design asks (an experiment, a metric). A single design item takes a fast path with no project map. The outputs are `experiment-spec.md` and `metric-spec.md`.
77. A spec never holds an invented number. Baselines, targets and benchmarks come from the user or the data map, or are marked "to confirm". A proxy is a guess until a check shows it tracks the true metric, and the spec says how to check.
78. One routing guide, in the README and in `/ask-data-skills`: a project or a design goes to `/wayfinder-data`, one question with a decision goes to `/grill-the-ask`, unsure goes to `/ask-data-skills`. `/grill-the-ask` sends project-sized and design asks to `/wayfinder-data` with one line why.

## Build decisions

Format: decision, options, reason.

B1. Branch: use `spec/v0` as asked, not the session default branch. Options: session branch or `spec/v0`. Reason: the task names it and the PR is from it.
B2. Upstream access: cloned both upstream repos and `caltunay/datafolx` read-only via the git proxy. Options: skip or clone. Reason: needed for licenses and reuse.
B3. Upstream licenses: Anthropic `data` plugin is Apache-2.0. OpenAI `data-analytics` has no license file and `plugin.json` says "Proprietary". Options: reuse text, or ideas only. Reason: we copy no text from either. NOTICE credits Anthropic as a courtesy plus other inspirations. OpenAI is ideas only.
B4. Nested skill discovery (open item 1): use flat `skills/<name>/`. Options: flat or nested. Reason: SPEC says flat if unsure, and I could not test the installer here.
B5. Template location (open item 2): `DATA-MAP.template.md` lives in `skills/data-map/`. `analysis.template.md` lives in `templates/` (SPEC 16) and a copy sits in `skills/grill-the-ask/`, because that skill creates the file and an installer may copy only skill folders. `scripts/package-zips` and the self-check verify both copies match. Each skill also lists the section names inline as fallback.
B6. sqlstyle.guide (open item 4): the site was unreachable from this session. From memory it is CC BY-SA 3.0, which is share-alike. Decision: quote nothing, summarise rules in our own words, link to it. Options: quote, or paraphrase. Reason: avoids a license obligation I could not verify.
B7. Plugin manifests (open item 5): not added. Options: add or v1. Reason: not trivial to verify without the tools. Deferred to v1.
B8. Descriptions (open item 6): each starts with the situation, flow skills say "Use only when the user runs /<name> or explicitly asks to ...", disciplines name concrete triggers and say they are called by the flow. See each SKILL.md.
B9. datafolx reuse: adapted the review protocol, technical and business review, methods, and the planted-flaw case designs. Rewrote all text. The word is never used outside SPEC.md and DECISIONS.md. Invented data only.
B10. Eval cases live in `evals/<skill>/case-N.md` with `rubric.md`. Each case holds an input and a pass description. Planted-flaw cases for `review-analysis` are adapted from the earlier cases.
B11. Added `scripts/self-check`, not in SPEC 16. Options: manual checks only or a script. Reason: repeatable, and the PR can show the output. It is not packaged into any skill.
B12. Em dash check skips `SPEC.md` because it must stay unchanged. It has none anyway.
B13. Skill commands are named in descriptions with a trailing space check ("Use only when the user runs /<name> or explicitly asks to ..."), which the self-check matches.
B14. Install docs for Codex, Gemini CLI, Cursor and Copilot give the `npx skills add` route and say to check each agent's current docs for the exact folder. I could not verify folder paths from this session, so I avoided stating them as fact.
B15. Chat-app ZIP upload steps in `docs/install.md` describe the general route. Exact menu names change, so they are not pinned.
B16. The eval cases are written as inputs plus pass and fail descriptions. They are run by hand (SPEC 15), so there is no runner. Results go in `evals/results/`, which is empty until the maintainer runs them.
B17. No manual run of the evals in the four agents was possible from this session. The manual test checklist in the PR is for the maintainer.

### v0.2 build

B42. Setup (v0.2 item 0). Branch `v0.2` from the finished `spec/v0`. SPEC section 20 describes the v0.2 items. Design decisions 33 to 46 appended. The brief lists 13 items; SPEC 20.14 adds the catalogue count.
